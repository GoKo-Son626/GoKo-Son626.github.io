星上时间访问服务（SOIS TAS）：时间关联、服务原语与时间编码

在由多个处理器、数据系统和星载设备组成的航天器中，时间不仅用于显示日期或记录日志，更是任务调度、遥测时间标记、载荷数据关联和分布式协同的基础。各处理节点通常拥有独立的本地时钟；如果没有统一的时间关联机制，不同节点对同一事件的时间认知就可能出现偏差。

CCSDS SOIS（Spacecraft Onboard Interface Services）提出的 Time Access
Service（TAS，时间访问服务），其核心目标不是规定某种具体时钟硬件或同步协议，而是为星载应用提供统一的本地时间访问接口，使应用不必直接操作处理器上的计数器寄存器，也不必了解底层时间源的硬件实现。

本文以 CCSDS 872.0-M-1《Spacecraft Onboard Interface Services—Time
Access Service》为主要依据，结合其明确引用的 CCSDS 853.0-M-1《Subnetwork
Synchronisation Service》和 CCSDS 301.0-B-4《Time Code
Formats》，讨论星上时间体系的分层关系、本地时间源与主时间源、PPS
加时间消息的典型关联机制、TAS
服务原语、可选闹钟与节拍器能力、管理参数、服务性能表征，以及 CUC
时间码在数据交换中的位置。

本文特别强调三个边界：

  • 时间访问：应用如何读取和使用本节点的时间，由 Time Access Service
    抽象。
  • 时间关联与分发：多个节点如何获得共同的时间认知，由底层同步机制和相关服务承担。
  • 时间编码：时间如何被表示并装入遥测或其他数据结构，由 CCSDS
    时间码格式等规范定义。

cFS与SB学习记录（六）：SB自己的任务在做什么，NOOP和HK怎样走一圈

在前几篇里，发送应用直接调用 SB API，消息就进入了接收管道。这很容易带来一个新疑问：源码中为什么还需要一个 CFE_SB_TaskMain()？所有应用的消息是否都要先经过这个任务转发？

我把这两条路径分开以后才看清楚：应用调用的发送函数在调用者的执行上下文里完成路由和投递；SB 自己的任务处理的是给 SB 的管理请求。它也使用管道和订阅机制，算是软件总线上的一个服务使用者。

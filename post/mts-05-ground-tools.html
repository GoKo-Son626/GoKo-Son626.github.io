如果地面工具只处理一种固定消息，可以在程序里直接写明结构体和类型。任务中的命令越来越多时，更通用的办法是让工具依据数据库查询接口、类型和字段，再完成赋值、编码和传输。这篇沿着命令构造和遥测解码两条方向，记录这种工具需要哪些信息。

用一个例子区分名字、类型和消息标识

假设操作员输入“某处理器实例上，向 SB 的命令接口发送某个具体命令”，并附带 字段=值。这里至少有四件事：实例标识目标位置；接口标识目标通信端点；具体命令名决定派生消息类型；字段名决定要写入的业务成员。它们不能和最终 MsgId、EdsLib 类型 ID 混用。

这不是所有 EDS 应用都必须走的路径。固定类型的小程序可以直接取得已知类型；通用工具需要额外的名字数据库和任务接口映射。DisplayDB 帮助按名字定位字段，DataTypeDB 描述类型和编码，MissionLib/接口数据库连接任务的接口与 Topic。查找失败应中止发送，而不是用猜测的数值继续。

为什么要先选类型、再写字段

一种常见命令体系把公共命令头定义为基类型，把不同功能码的命令定义为派生类型。工具先查接口的参数基类型，再选择具体类型；初始化该具体类型时，模型中的固定值约束才有机会写入对象。随后才能根据该类型定位载荷成员并转换输入。

cmdUtil.c 先按本地 Payload 类型查字段，再把字符串转到完整命令缓冲里的相应成员。摘录省略中间的错误返回。

字段偏移以 native 对象中的字节为单位。定位完整对象中的字段时，先取 Payload 的 native 偏移，再加成员在 Payload 内的 native 偏移。核对过的工具会记录参数解析或字段转换失败，但参数处理函数未把失败状态传回外层发送流程。若要让任一无效参数阻止发送，须先把错误逐层返回，再决定是否打包。

历史工具修复记录里有一个值得保留的边界：接口参数类型并非总有派生子类型。如果工具不区分“需要从多个派生项选择”和“本身就是完整类型”，就可能把合法的 SEND_HK 拒绝。历史处理按数据库中的派生项数量决定是否要求命令子类型，并检查初始化与 Pack 返回码。这个例子解释的是该任务模型和工具实现，不代表所有接口都能忽略具体类型。

发送前的 PackCompleteObject() 则有明确的失败分支。它接收本地对象的字节大小和打包缓冲的位容量。

遥测为什么要分两次解码

接收端可能事先不知道完整遥测类型，但所有候选消息有可识别的公共头。一种实现是先解公共头，取得发布参数或 MsgId，再通过任务映射查 Topic、接口和消息类型，随后继续解出具体消息，执行校验并按字段遍历显示：

tlm_decode.c 两次调用同一个部分解码接口。第一次从头开始，中间查询发布者的 Topic 和参数类型，第二次使用查到的 EdsId 续解。摘录省略查询和返回值检查。

两次的 8 * n 都表示实收字节数换算成的位数。第二次的 TypeInfo.Size.Bytes 来自此前查询的公共头 native 大小，用来指定续解位置。

解码完成后，原工具调用 EdsLib_DataTypeDB_VerifyUnpackedObject() 检查特殊字段。校验失败时打印告警，随后仍遍历字段。因此屏幕上出现字段值，只能说明工具显示了结果。判断该包是否通过校验，还要看状态和告警。

以 NOOP 和 SEND_HK 对照类型选择

cpu1:CFE_SB/CMD.NoopCmd 包含实例、CMD 接口与具体派生命令；cpu1:CFE_SB/SEND_HK 使用另一个接口，不能因为名字里没有命令后缀就一概拒绝。先查询该接口参数是否存在派生项，再决定选择过程，最后检查初始化和 Pack 状态。

接收侧不是“看到一个 MsgId 就天然知道所有字段”。公共头提供查任务映射的输入，任务数据库给出接口及参数类型，DataTypeDB 完成后续解码，DisplayDB 才能按字段名显示。若地面用了另一批数据库，即使类型 ID 数字相同，也不能据此认为模型一致。

基础 API 的完整单位、初始化与错误处理见EdsLib 打包解包。本篇关注任务接口查询，和固定 PUS 类型的 UDP 实验有不同前提。

在由多个处理器、数据系统和星载设备组成的航天器中，时间不仅用于显示日期或记录日志，更是任务调度、遥测时间标记、载荷数据关联和分布式协同的基础。各处理节点通常拥有独立的本地时钟；如果没有统一的时间关联机制，不同节点对同一事件的时间认知就可能出现偏差。

CCSDS SOIS（Spacecraft Onboard Interface Services）提出的 Time Access
Service（TAS，时间访问服务），其核心目标不是规定某种具体时钟硬件或同步协议，而是为星载应用提供统一的本地时间访问接口，使应用不必直接操作处理器上的计数器寄存器，也不必了解底层时间源的硬件实现。

本文以 CCSDS 872.0-M-1《Spacecraft Onboard Interface Services—Time
Access Service》为主要依据，结合其明确引用的 CCSDS 853.0-M-1《Subnetwork
Synchronisation Service》和 CCSDS 301.0-B-4《Time Code
Formats》，讨论星上时间体系的分层关系、本地时间源与主时间源、PPS
加时间消息的典型关联机制、TAS
服务原语、可选闹钟与节拍器能力、管理参数、服务性能表征，以及 CUC
时间码在数据交换中的位置。

本文特别强调三个边界：

  • 时间访问：应用如何读取和使用本节点的时间，由 Time Access Service
    抽象。
  • 时间关联与分发：多个节点如何获得共同的时间认知，由底层同步机制和相关服务承担。
  • 时间编码：时间如何被表示并装入遥测或其他数据结构，由 CCSDS
    时间码格式等规范定义。

1. 标准依据与适用状态

1.1 三份文件分别规定什么

本文涉及的三份 CCSDS 文件处于不同的技术层次。

文件 文件类别 业务范围
872.0-M-1 原 Magenta Book，现归档 应用怎样访问本地星上时间
853.0-M-1 Magenta Book 子网时间信息与事件通知
301.0-B-4 Blue Book CUC、CDS、CCS 和 ASCII 时间码

其中，872.0-M-1
才是名称和内容都直接对应”卫星时间访问服务”的文件。301.0-B-4
是时间码格式标准，不是时间访问服务规范。

1.2 必须注意的版本和状态问题

CCSDS 872.0-M-1 于 2011 年 1 月发布，属于 Magenta Book，即 Recommended
Practice（推荐实践）。CCSDS 提供的归档 PDF 明确标注为
CCSDS Historical Document；CCSDS 官方 Silver Books 页面也将其列入
Historical—Obsolete 类别。其对应的 ISO 17214:2011 也已被 ISO 标记为
Withdrawn（撤销）。

这意味着：

  1. 872.0-M-1 仍然是理解 SOIS
    时间访问服务设计思想和接口模型的重要原始资料；
  2. 不能仅凭它曾经是 CCSDS 文件，就把它称为当前有效的强制性标准；
  3. 如果某个项目或客户明确采用该文件，应进一步核对项目基线、接口控制文件（ICD）、符合性要求及客户指定的文件版本；
  4. 历史文件被归档，并不自动意味着既有工程实现失效，但新项目不能忽略文件状态和项目适用性审查。

CCSDS 853.0-M-1 于 2009 年 12 月发布，官方 SOIS 出版物目录仍将其列在
SOIS 推荐实践出版物中。它是理解 872.0-M-1
所依赖的子网时间同步服务的重要配套资料。

CCSDS 301.0-B-4 于 2010 年 11 月发布，属于 Blue Book 推荐标准。CCSDS
官方目录将该版本列为时间码格式推荐标准。对应的 ISO
11104:2011 在 ISO 页面上显示于 2023
年复审确认后继续有效。需要注意，时间码格式标准仍然不负责规定时钟同步性能。

术语说明： CCSDS 的 Magenta Book 是 Recommended Practice，Blue
Book 是 Recommended
Standard。二者文件类别不同。推荐实践本身并不自动成为某个项目的强制要求；是否具有项目约束力，仍取决于任务规范、合同、ICD
或适用的上层标准。

2. 为什么航天器需要时间访问服务

2.1 多处理节点会产生多个本地时间源

现代航天器通常不是只有一个处理器。不同数据系统可能分别承担姿态控制、载荷管理、数据处理、通信管理、遥测采集等任务。

每个处理节点都可能拥有自己的硬件计数器和本地振荡器。即使这些计数器具有相同的位宽和名义频率，它们也不一定在同一时刻启动，也不一定具有完全相同的实际频率。

例如：

节点 上电时刻 本地计时器初值 振荡器实际频率
处理器 A 任务时刻 0 s 0 10 MHz + 偏差 A
处理器 B 任务时刻 2 s 0 10 MHz + 偏差 B
处理器 C 任务时刻 5 s 0 10 MHz + 偏差 C
如果每个节点只读取自己的计数器：
  • A 的计数值 1000 s；
  • B 的计数值 998 s；
  • C 的计数值 995 s；

那么这些数字并不代表同一个任务时间坐标。它们只是各自从不同上电时刻开始累计的本地时间。

此外，晶体振荡器存在频率误差和长期漂移。即使节点在某个时刻被校准到相同时间，运行一段时间后也可能再次出现偏差。

2.2 主星上时间源与本地时间源

CCSDS 872.0-M-1 给出的典型架构包含：

  • 一个集中维护的 Master Onboard Time Source（主星上时间源）；
  • 分布在各数据系统中的 Local Time Source（本地时间源）；
  • 每个节点上的 Time Access Service；
  • 使用时间服务的任务应用。

主星上时间源是星上任务运行所采用的时间参考。本地时间源则位于各处理节点，用于让本节点应用能够直接、低开销地读取时间。

典型本地时间源可以是由本地晶体振荡器驱动的自由运行硬件计数器，累计秒和亚秒。主时间源也通常采用类似计数器，但其振荡器具有更好的绝对频率准确度和稳定性。

主时间源提供的时间在这份历史文档中列出两个称呼：

  • MET（Mission Elapsed Time，任务经过时间）；
  • 或 SCET（Spacecraft Elapsed Time，航天器经过时间）。

本文沿用 872.0-M-1 §2.3 的术语。其他任务和资料也可能用 SCET 表示 Spacecraft Event Time。字段的时间尺度、纪元和含义要以任务 ICD 为准。

2.3 Time Access Service 的核心价值

如果每个应用都直接读取硬件寄存器，会带来几个问题：

  1. 应用必须知道硬件计数器地址、位宽、计数格式和访问方法；
  2. 不同处理器上的应用可能使用不同的时间读取代码；
  3. 硬件更换或处理器迁移时，应用可能需要修改；
  4. 多个应用直接访问共享硬件资源，会增加平台管理和验证难度；
  5. 应用容易把本地计数器误认为已经与全星统一时间关联。

TAS 的设计目标是把硬件时间访问封装起来，向应用提供统一服务接口。

应用只需要知道如何请求时间、如何接收时间结果，而不必了解本地时间源是
FPGA 计数器、SoC 定时器、RTC 还是其他硬件实现。

3. Time Access Service 在 SOIS 架构中的位置

3.1 TAS 位于 Application Support Layer

SOIS 将 Time Access Service 放在 Application Support
Layer（应用支持层）。它面向上层任务应用，向应用提供访问本地时间源的服务。

与它相邻的还有消息传输、命令与数据采集、文件与包存储等服务。SOIS
的目标之一，是让飞行软件通过统一服务接口使用底层设备和子网能力，减少应用与具体硬件、链路的耦合。

从职责上看，可以把典型时间体系理解为：

这张图表达的是逻辑职责关系：

  • 主时间源提供任务采用的参考时间；
  • 子网同步机制使各节点的本地时间源与共同参考保持关联；
  • 各节点 TAS 访问本节点的本地时间源；
  • 应用通过 TAS 获取时间。

它不是说应用每次读取时间时，都要通过网络向主时间源发起一次远程查询。恰恰相反，典型架构是在每个节点维护本地时间源，由同步机制周期性地进行时间关联，应用读取本地时间即可。

3.2 TAS 不负责产生时间，也不负责同步时间

这是理解 872.0-M-1 最关键的一点。

该文件明确限定了 TAS 的范围：

  • 它定义应用与本地时间源之间的服务接口；
  • 它不规定主时间源和本地时间源具体由什么硬件实现；
  • 它不规定各时间源之间采用什么算法进行关联；
  • 它不规定通过哪一种总线或网络传递时间；
  • 时间源之间的关联机制由相关底层同步服务处理。

因此，以下几个概念必须分开：

层次 主要职责 例子
时间源 产生计数 振荡器、硬件计数器、RTC
时间关联 将本地时间关联到共同参考 PPS 与时间消息、PTP
时间访问 向应用提供统一接口 SOIS TAS、平台时间 API
时间编码 序列化时间值 CUC、CDS、CCS

如果把这四层混在一起，就容易出现”有了时间访问 API
就已经完成多处理器同步”这样的错误理解。

4. 本地时间源的硬件实现与时间关联

4.1 自由运行计数器

872.0-M-1 的附录 B
给出了典型本地时间源实现方式：使用本地晶体振荡器驱动自由运行计数器。

计数器可以分成：

  • Seconds：整秒计数；
  • Sub-seconds：秒以下计数。

一个简化表示为：

T = S + F

其中：

  • S 表示整秒；
  • F 表示当前秒内的分数部分。

假设本地时钟频率为 10 MHz，那么每秒会产生约 10,000,000
次计数。硬件可以根据计数器配置，把计数值换算成秒和亚秒。

自由运行计数器的优点是：硬件持续计时，不需要软件每隔很短时间主动更新一次时间值。

但自由运行不代表准确。计数器的实际走时取决于振荡器频率，而不同节点的振荡器频率和稳定性可能存在差异。

4.2 872 文档中的 32 位计数器示例

872.0-M-1 附录 B 给出一个便于理解的示例：

  • 总计数宽度：32 bit；
  • 整秒部分：24 bit；
  • 亚秒部分：8 bit。

8 bit 亚秒部分可以表示一秒内的 256 个分数单位：

亚秒分辨率为 1 s / 2⁸ = 3.90625 ms。

因此，其时间分辨率略小于 4 ms。

24 bit 秒计数的回绕周期为：

回绕周期为 2²⁴ s = 16,777,216 s ≈ 194.18 天。

这只是文档给出的典型实现示例，不是 TAS 强制要求所有设备都使用 32
位计数器，也不是对所有任务的精度要求。

这个例子说明：时间计数器的位宽、秒字段和亚秒字段长度，直接决定时间表示的分辨率和回绕周期。

4.3 为什么需要一个主时间源

假设三个处理器都使用 10 MHz 计数器：

  • A 的实际频率略快；
  • B 的实际频率略慢；
  • C 的启动时间晚于 A 和 B。

如果没有统一参考，各节点即使在某一时刻计数值相同，也不能保证之后仍然一致。

因此，需要选择一个主星上时间源作为任务时间参考，并建立机制使各节点的本地时间源与其关联。

872.0-M-1 将这种过程称为 Time
Correlation（时间关联）：维护主时间源与各本地时间源之间的一致性，使各时间源在规定的不确定度范围内给出相同的时间值。

这里的”相同”不是数学意义上的绝对相等，而是满足任务规定的误差范围。

5. PPS 加时间消息：872 附录 B 给出的典型方案

5.1 为什么要同时有时间消息和 PPS

PPS（Pulse Per
Second，秒脉冲）是每秒产生一次的硬件脉冲信号。它提供一个精确的整秒边界，但单独的
PPS 不包含”当前是第几秒”这样的完整时间信息。

因此，典型方案需要两种信息：

  1. 时间消息：告诉各节点下一次有效脉冲对应的整秒数值；
  2. PPS 信号：告诉各节点这个时间值从哪个准确的物理时刻开始生效。

872.0-M-1 附录 B 给出的例子是：

  • 主时间源通过航天器数据处理总线广播参考 MET 的整秒值；
  • 一个专用 PPS 信号分发到各节点；
  • 文档举例使用 MIL-STD-1553B 总线广播整秒值。

这是一种典型实现示例，不代表标准强制所有任务使用
MIL-STD-1553B，也不代表所有星载系统必须使用相同的脉冲电气接口。

5.2 从时间消息到本地计数器更新

本地时间源通常包含：

  • Local Time Counter：本地时间计数器；
  • Datation Register：定时装载寄存器；
  • Local Crystal Oscillator：本地晶体振荡器；
  • PPS Input：秒脉冲输入。

处理过程如下：

  1. 主节点广播参考时间的整秒值；
  2. 从节点接收该时间值，将其写入 Datation Register；
  3. PPS 有效边沿到来；
  4. 本地时间源把 Datation Register 中的整秒值装入本地计数器的 Seconds
    部分；
  5. 同一时刻清零 Sub-seconds 部分；
  6. 本地晶体振荡器继续驱动计数器运行；
  7. 下一次 PPS 到来时再次进行关联。

注意：时间消息必须与对应的 PPS
边沿正确关联。若消息和脉冲没有明确的对应关系，就可能产生整秒错位。

5.3 为什么不能在收到软件消息时直接清零

如果只通过普通总线消息传递”当前时间是 101
秒”，然后各节点在各自收到消息的瞬间清零计数器，那么不同节点的清零时刻会受到总线传输延迟、仲裁、驱动处理和任务调度影响。

例如：

节点 收到时间消息的时刻
A 100.0002 s
B 100.0010 s
C 100.0025 s
如果各节点在收到消息时立即清零，它们的本地秒边界就不一致。

PPS
的作用就是提供共同的物理边沿，使节点能够在同一同步事件上装载整秒值并清零亚秒计数。

5.4 两次 PPS 之间仍然存在漂移

PPS 并不会让本地振荡器变得完全准确。

在两次 PPS
之间，本地计数器仍由自己的晶体振荡器驱动。由于振荡器存在频率误差，本地时间会逐渐偏离主参考。

下一次 PPS 到来时，再次进行时间关联。

因此：

  • PPS 间隔越长，振荡器误差积累的时间通常越长；
  • 振荡器稳定性越好，两次同步之间的时间漂移通常越小；
  • 实际最大偏差需要通过硬件指标、温度范围和任务要求计算或测试。

872.0-M-1
还指出，较完善的本地时间源可以检测漏掉的时间关联步骤，并设计成关联过程不会让对外报告的时间倒退。但这些技术超出了该附录的简要实现说明范围。

6. Time Access Service 的服务模型

6.1 Service User 与 Service Provider

TAS 采用服务用户和服务提供者之间的请求/指示模型：

  • Service User：请求访问时间的上层应用；
  • Service Provider：实现 Time Access Service 的软件实体；
  • TASAP：Time Access Service Access Point，时间访问服务接入点。

TASAP Address 用于标识希望调用时间访问服务的用户实体。

这里的 Service
Primitive（服务原语）是服务接口层面的抽象描述。它规定用户和提供者之间交换什么操作、参数和结果，并不意味着每个原语都必须被实现成一条独立的网络报文。

6.2 必选能力：Wall Clock

872.0-M-1 规定，Time Access Service 必须实现 Wall Clock Capability。

Wall Clock
在这里表示按需读取本地星上时间的能力。它不意味着返回值一定是人类日常使用的
UTC 日历时间；底层时间源也可以是从任务 Epoch 开始累计的经过时间。

基本交互为：

TIME.request

功能：请求服务提供者读取当前时间。

参数：

  • TASAP Address：标识请求服务的用户接入点；
  • Transaction Identifier：由用户分配，用于关联请求和后续响应。

服务提供者收到请求后，确定当前时间。

TIME.indication

功能：向用户返回当前时间。

参数：

这五项信息不能只看成”返回一个时间值”。

参数 作用
TASAP Address 标识服务用户
Transaction Identifier 关联结果与原请求
Current Time 服务提供者给出的当前星上时间
Current Time Error Specification 服务提供者给出的时间误差说明
Result Metadata 表达请求成功、失败或异常

其中，Current Time Error Specification 尤其值得注意。

它说明时间访问服务不应只向应用返回一个数字，还应能表达这个时间值的误差情况。否则，应用虽然拿到了时间，却无法判断其可信程度。

Result Metadata
则用于表达操作结果。文档举例包括：请求没有在规定的管理超时内完成，或者
Time Access Service 本身工作异常。

872.0-M-1
没有把所有项目的误差字段编码格式、单位和内部数据结构统一规定成一个具体二进制结构。具体协议或实现需要定义这些细节，并与项目时间要求保持一致。

7. 可选能力一：Alarm Clock

7.1 Alarm Clock 解决什么问题

Alarm
Clock（闹钟能力）允许应用注册一个未来时刻，并在该时刻获得一次时间通知。

它不是简单地让应用反复调用 GetTime()
判断是否到达目标时间，而是把”在指定时刻通知我”交给时间访问服务处理。

872.0-M-1 允许 Alarm-At Time 使用绝对时间或相对时间。

例如：

  • 绝对时间：在任务时间 1200 s 时通知；
  • 相对时间：在当前时间之后 10 s 通知。

9.1 TAS 的服务参数

参数 作用

Transaction Identifier 关联请求与响应
Alarm Identifier 标识已创建的一次性闹钟
Metronome Identifier 标识已创建的周期通知
Result Metadata 描述服务操作结果

Current Time Error Specification 当前时间值的误差说明

这些参数体现了 TAS

9.2 TAS 的 MIB 并没有被统一定义成固定数据结构

872.0-M-1 第 4 节有一个容易忽略的说明：

该服务本身目前没有单独定义一套完整的 Management Information
Base（MIB）。如果某个协议声称以 SOIS 兼容方式提供 Time Access
Service，那么提供该服务的协议应在自己的协议规范中发布相应 MIB。

872 文档给出的 MIB 设计指导包括三个方面：

  1. Frequency；
  2. Drift；
  3. Maximum Adjustment。

它们的含义如下。

Frequency

Frequency 表示 Time Access Service 更新或采样本地时间源的频率。

特别注意：这里的 Frequency 不是本地硬件晶体振荡器的频率。

例如：

  • 本地硬件时钟频率：10 MHz；
  • TAS 每秒采样或更新服务数据：100 次。

这里 10 MHz 是硬件计数器时钟频率；100 Hz
才是该服务参数所描述的更新频率。

Drift

Drift 表示本地时钟所使用振荡器的稳定性。

振荡器存在频率误差，时间运行一段时间后就会产生累积偏差。MIB
应能够提供相关漂移信息；文档还指出，管理实体可以更新该参数，以补偿时钟老化带来的影响。

Maximum Adjustment

Maximum Adjustment
表示允许对本地时间源进行的最大时间调整量，可以向前调整，也可以向后调整。

如果直接把本地时间从 1000.000 s 调整到 999.900

因此，时间调整需要受到管理约束，不能不加控制地改变应用可见的时间。

9.3 时间跳变、单调性和应用影响

本地时间源通常希望表现为持续向前的时间计数，但 872.0-M-1
也明确指出，底层本地时钟可能因为校正而被向后调整。

工程上至少要区分：

  • 时间值：当前本地时钟给出的时间；
  • 时间偏差：本地时间与主时间参考之间的差异；
  • 频率偏差：本地时钟走快或走慢的程度；
  • 时间调整：为了修正偏差而对本地时钟进行的操作。

如果应用使用时间值计算两个事件之间的间隔，就必须考虑时间调整是否可能造成倒退或跳变。

因此，工程设计通常还需要明确：

  • 哪些时间 API 返回任务统一时间；
  • 哪些 API 用于测量本地时间间隔；
  • 是否允许运行期间向后校时；
  • 最大调整量是多少；
  • 应用如何识别时间无效或时间误差超限。

这些具体策略需要由任务和平台实现确定，不能仅靠 872
文档中的抽象接口自动获得。

10. 服务性能：返回时间正确，不代表访问过程没有延迟

10.1 时间访问服务本身也有延迟

872.0-M-1 附录 D 专门讨论了 Service Characterization（服务性能表征）。

它指出，时间访问服务返回的时间值与这个值实际交付给应用的时刻之间存在时间关系。

理想情况下，应用发出请求后，服务能够像直接读取硬件计数器一样立即得到时间；但真实系统中，时间访问过程会经过：

  • 应用调用；
  • 服务接口处理；
  • RTOS 或基础软件；
  • 硬件计数器读取；
  • 结果返回和应用调度。

因此，从实际时间事件发生到应用收到 TIME.indication
之间必然存在一定延迟。

10.2 必须区分时间误差和服务访问延迟

指标 测量对象 主要影响因素
时间源误差 本地时间与主参考的差值 振荡器、温度、校准和同步周期
时间分辨率 时间值能表示的最小单位 计数器与亚秒字段
时间访问延迟 请求发出到结果送达 调度、负载与服务实现
Alarm 通知延迟 事件发生到通知送达 定时器、中断与调度
Metronome 周期误差 实际间隔与请求间隔的差值 时钟、定时器与调度抖动

一个系统即使具有高精度硬件时钟，也可能因为服务调用和任务调度延迟，使应用收到时间结果时已经过去了一段时间。

反过来，服务响应很快，也不代表底层时间源本身足够准确。

10.3 附录 D 建议测量的两类延迟

附录 D 给出了至少应当考虑的两项测试：

  1. TIME.request 到对应 TIME.indication 之间的最大时间；
  2. Alarm 或 Metronome 事件实际发生到用户通过 TIME.indication
    收到通知之间的最大时间。

这些测试结果应与真实系统的性能需求进行比较。

因此，时间访问服务的验证不能只测”返回的秒数对不对”，还要测：

  • 请求到响应的最大延迟；
  • 闹钟触发到通知的最大延迟；
  • 周期通知的实际间隔；
  • 不同 CPU 负载下的性能变化；
  • RTOS 调度和中断对服务延迟的影响。

12. CCSDS 853.0-M-1：与时间访问服务配套的子网同步服务

12.1 为什么还需要 Subnetwork Synchronisation Service

前面已经说明，872.0-M-1
只定义应用访问本地时间源的接口，并不负责把不同处理器的时间关联起来。

因此还需要底层的时间同步/关联机制。

CCSDS 853.0-M-1《Spacecraft Onboard Interface Services—Subnetwork
Synchronisation Service》定义了 SOIS 子网同步服务。

它的核心功能是：

为用户实体提供一种机制，使其能够维护在同一子网中各数据系统之间共同的时间认知。

该服务通过子网使用的数据链路传递时间数据和控制信息。具体采用哪种数据链路和传输协议，不属于
853.0-M-1 本身规定的实现范围。

12.2 853 与 872 的职责区别

这两个文件都出现 TIME.request 和
TIME.indication，但它们属于不同服务层次，不能因为名字相同就认为语义完全相同。

对比项 872.0-M-1 TAS 853.0-M-1 Subnetwork Synchronisation
所在层次 应用支持层 子网层
服务接入点 TASAP SYNCSAP
时间请求 TIME.request(TASAP, Transaction ID) TIME.request(SYNCSAP)
时间指示 本地时间、误差和结果 子网时间数据，可主动指示
其他能力 可选 Alarm 和 Metronome Event 请求和事件通知

可以把二者理解为：

  • 853 解决”子网中的节点如何获得共同时间信息”；
  • 872 解决”节点上的应用如何统一访问本地时间”。

12.3 853 的时间原语

853.0-M-1 定义了两个时间原语：

用户请求子网同步服务获取时间数据。

服务提供者向用户传递时间数据。

其中，TIME.indication 不仅可以响应
TIME.request，还可以在没有请求的情况下主动发出。例如，采用时间广播系统时，服务提供者可以周期性地向子网用户发布时间信息。

12.4 853 还包含 Event 通知能力

853 并不只有时间数据传递，还定义了子网事件通知：

用户可以请求开始或停止接收某个子网事件的通知。

发生事件后，服务提供者通过：

通知用户。

其中：

  • Event ID：标识发生的事件；
  • Event Time：表示事件发生的时间；
  • Event Data：携带与事件有关的数据；
  • Start/Stop：控制是否开始或停止接收指定事件通知。

这说明 SOIS Subnetwork Synchronisation Service
的设计并不局限于时间查询，也包括子网级事件通知。

12.5 853 的 Best-effort 服务质量非常重要

853.0-M-1 明确规定，该同步服务采用单一 Best-effort QoS。

这意味着服务只尝试提供所请求的能力，不能保证一定成功完成。

它没有在服务原语中提供独立的 Channel 和 Priority
参数。若具体子网需要优先级、资源预留或信道管理，应由相应子网管理信息和协议实现处理。

因此，不能仅仅因为采用了 853
的同步服务接口，就推断时间消息必然可靠到达，也不能推断其传输时延具有确定上界。

如果任务对时间同步的可靠性和精度有严格要求，具体链路协议、硬件实现、错误检测和恢复机制必须进一步定义和验证。

12.6 853 同样没有规定唯一的底层协议

853.0-M-1 的范围是服务及其服务接口，不规定不同数据链路上如何实现该服务。

它要求具体协议如果声称以 SOIS
兼容方式提供同步服务，就应在协议规范中发布相应 MIB。

MIB 指导内容包括：

  • 通道资源分配；
  • Time 的语义；
  • Event Time 的语义；
  • Event ID 和 Event Data 的语义；
  • 同步 PDU 的优先级和信道分配；
  • 主动发送 TIME.indication 的周期或触发条件。

所以，853 是一个服务抽象和接口规范，不是一个可以直接替代
1553、SpaceWire、CAN 或以太网协议的具体传输协议。

13. CCSDS 301.0-B-4：时间访问服务返回的时间如何编码

13.1 时间访问与时间编码是两个问题

时间访问服务返回的是一个时间值。

但当这个时间值需要放入遥测包、记录文件或通过链路发送时，就必须规定：

  • 时间字段占多少字节；
  • 秒和亚秒如何编码；
  • 时间从哪个 Epoch 开始；
  • 使用什么时间尺度；
  • 接收方如何识别时间码格式。

CCSDS 301.0-B-4《Time Code
Formats》就是为时间数据交换提供统一编码格式的标准。

它明确指出，时间码是时间信息的数字表示；该标准不负责规定时间稳定性、精度和准确度等性能指标。

1958 年 1 月 1 日 TAI。

其推荐基本时间单位为秒。

这个 CUC Level 1 时间码使用 TAI 作为参考时间尺度，不以 UTC
为基础，因此不需要在该时间码中进行闰秒修正。

这点在工程中非常重要。

如果发送端把时间理解为 UTC，接收端却把同一字段按 TAI
解释，那么双方可能产生秒级偏差。

因此，时间码字段不能只约定”前 4 字节是秒、后 2 字节是亚秒”，还必须明确：

  • Epoch；
  • 时间尺度；
  • 粗时间字段长度；
  • 精时间字段长度；
  • P-Field 是否存在；
  • 字段字节序；
  • 任务是否采用 Agency-defined Epoch；
  • 相关元数据由哪里提供。

一个 CUC 4+2 字节的对照片段

假定任务已声明基本单位为秒、P-Field 省略、粗时间 4 字节、细时间 2 字节。字节串 00 00 00 05 80 00 中，粗时间是 5，细时间整数是 0x8000。以 2¹⁶ 为分母得到 0.5 秒，整个字段表示距任务约定纪元 5.5 秒。两字节细时间的分辨率为 2⁻¹⁶ 秒，约 15.26 μs。这个数字描述编码能表达的最小步进，实际时间误差仍由时间源与同步结果决定。PUS 遥测时间字段

13.5 301 标准不负责时间同步

这里必须再次强调：

  • 301 规定时间值如何编码；
  • 872 规定应用如何访问本地时间；
  • 853 规定子网同步服务如何提供共同时间信息。

即使所有设备都使用相同的 CUC
格式，如果各设备的本地时间源没有正确同步或关联，它们编码出来的时间仍然可能不一致。

统一编码不能替代统一时间基准。

14. PTP、TSN 应该放在什么位置理解

IEEE 1588 PTP（Precision Time Protocol）和 TSN（Time-Sensitive
Networking）经常与星上时间同步一起讨论，但它们不是 CCSDS 872.0-M-1
所规定的强制实现方式。

更准确的理解是：

  1. 872 定义时间访问服务接口；
  2. 853 定义子网同步服务接口；
  3. 具体平台可以根据链路和硬件条件选择时间同步实现；
  4. 如果采用以太网网络时间同步，可以进一步研究 IEEE 1588 PTP；
  5. 如果需要时间敏感网络中的统一时钟和确定性流量调度，可以研究 IEEE
    802.1AS/gPTP 与 TSN 相关机制。

PTP
的典型功能是通过网络时间戳交换估算设备间的时钟偏差和路径延迟；硬件时间戳可以降低软件协议栈和任务调度带来的时间戳不确定性。

但需要注意：

  • PTP 是同步协议，不是时间访问 API；
  • 硬件时间戳与 PTP 协议版本是不同维度；
  • TSN 不只是时间同步，还包括时间感知流量调度等机制；
  • 采用 PTP 或 gPTP 并不自动意味着符合某个具体航天任务的 SOIS
    时间服务接口要求。

如果工程采用
PTP，需要把它放在底层时间同步/关联实现层进行设计，而不是把它直接等同于
TAS。

15. 面向工程实现的设计与验证要点

15.1 时间访问服务的建议模块边界

如果在星载软件中实现类似 TAS 的能力，可以将其划分为：

这是工程上的一种建议性分层，不是 CCSDS 规定的源代码目录或固定模块名称。

关键是把三个依赖隔离开：

  • 应用依赖服务接口；
  • TAS 核心依赖本地时间源抽象；
  • 本地时间源适配层依赖具体 RTOS 和硬件。

这样更换处理器或定时器硬件时，应用层不需要跟着修改。

15.2 需要明确的时间接口契约

实现前至少应当确定：

设计项 必须明确的问题
时间基准 使用 MET、SCET、TAI、UTC，还是任务自定义时间？
Epoch 时间从什么起点开始累计？
时间表示 秒和亚秒分别使用多少位？
误差表达 Current Time Error Specification 使用什么单位和格式？
时间有效性 何时认为时间有效，失步后如何标记？
时间调整 是否允许向前或向后调整，最大调整量是多少？
请求关联 Transaction Identifier 如何分配和回收？
Alarm 绝对时间和相对时间如何解释？
Metronome 周期以绝对时间还是间隔方式维护？
性能 最大访问延迟和通知延迟是多少？
回绕 秒计数器回绕时如何保持时间语义？
重启 处理器重启后，本地时间如何重新关联主时间？
如果这些内容没有定义清楚，即使服务原语名称与 CCSDS
文件一致，也不能说明接口已经满足项目的时间需求。

15.3 建议的验证项目

测试类别 注入或操作 观察内容
基本读取 发出时间请求 时间、事务标识与结果状态
误差报告 引入可测时钟偏差 报告的误差与测量值
请求并发 不同应用使用相同事务号 TASAP 与事务号正确关联
失败与超时 模拟时间源读取失败或响应超时 结果元数据能区分失败
Alarm 注册、触发、触发前取消 注册结果、通知时刻与取消结果
Metronome 指定首次时间与周期，再取消 周期、抖动与取消后的通知状态
PPS 关联与丢失 时间消息配合 PPS，随后模拟失步 整秒边界、时间质量与恢复
长期漂移与性能 改变负载并持续测量 时间偏差与请求、事件的最大通知延迟

15.4 最容易被忽略的四项验证

第一，时间值和时间误差必须一起验证。

只检查 Current Time
是否递增是不够的。还需要检查服务报告的时间误差是否与实际测量结果相符。

第二，服务响应延迟必须单独测量。

时间值可能是正确的，但应用收到它时已经过去了较长时间。特别是高负载下，RTOS
调度延迟可能明显增加。

第三，时间校正不能只验证”最终同步成功”。

还要检查时间是否发生倒退、跳变，以及应用是否能承受这些变化。

第四，必须验证失去同步后的行为。

PPS
丢失、主时间源失效或子网通信中断后，系统如何维持本地时间、如何报告时间质量、如何恢复同步，都应在任务级设计中明确。这里的
Holdover（守时）是工程上需要考虑的能力，不是 872.0-M-1
已经完整规定的一套状态机。

16. 关键结论

星上时间访问服务不是简单的”读取系统时间”函数，而是分布式星载软件体系中的一项基础服务。

理解它时，需要始终保持以下职责边界：

  1. 主星上时间源定义任务采用的参考时间；
  2. 本地时间源在各处理节点维护本地计数；
  3. 时间同步/关联机制使本地时间源与主时间源保持一致；
  4. SOIS Time Access Service向应用提供统一的本地时间访问接口；
  5. Alarm 和 Metronome为应用提供一次性和周期性时间通知；
  6. 管理信息和性能表征用于描述振荡器漂移、服务更新频率、最大校正量和服务延迟；
  7. CCSDS 301 时间码负责把时间值编码进数据交换结构。

其中最重要的关系是：

TAS 的价值在于把”如何访问时间”从具体硬件实现中抽象出来。

应用不再需要知道本地计数器位于哪个寄存器、使用哪一种振荡器、通过什么总线与主时间关联。它只需要遵循统一的服务接口，就能访问本节点的时间。

而真正决定星上多个节点能否保持时间一致的，是主时间源、本地时间源、底层同步机制及其性能验证。

Linux 已有成熟的线程与消息队列支持。把同一套上层逻辑放到另一个系统时，最容易出错的是接口语义、SDK 配置和最终链接。这里接着Linux 独立 SB 实验，整理一次 Starheart/Zynq QEMU 移植中真正需要重新检查的部分。

移植的是一组接口契约

SB 还需要路由、消息头接口、资源标识、配置、任务身份、池和事件。OSAL 则把任务、队列与信号量落实到目标系统。对于已在 Linux 篇解释的池和任务身份，这里只强调目标环境的核对方法：

接口 核对内容
任务身份 完整任务 ID 与应用登记是否匹配，是否考虑槽位复用
消息队列 深度、单项大小、非阻塞错误码和有限等待是否符合 OSAL 预期
信号量 创建、通知、限时等待及错误映射是否齐全
时间 名称与实际时基是否一致，超时能否依赖该时钟
内存池 锁归属、分配与归还、地址和偏移是否一致

例如示例需要两个接收者分别通知“订阅尝试结束”，计数信号量能保留两次通知；但协调者还要检查失败计数，ready 到齐不等于订阅成功。目标 SDK 已提供 POSIX semaphore 时可以考虑复用相应 OSAL 实现，前提是存储、ABI、错误与超时语义匹配。

目标源码有函数，不代表 SDK 可以使用

历史案例中，源码存在线程取消实现，SDK 头也可以给出声明，但取消组件没有按当前配置编入内核归档。沿功能配置、CMake 选源和 SDK 归档追到应用链接。Starheart 后端的 OS_TaskDelete_Impl() 保留了下面两步，省略日志和错误记录。

pthread_cancel() 提交取消请求，成功后才进入 pthread_join() 等线程退出。归档里可以先留下这两个符号引用，等最终链接器从目标 SDK 解析。

普通示例未调用任务删除路径，配合按函数分段和 --gc-sections，可以在未使用的删除代码被丢弃后完成链接。历史对照实验强制保留 OS_TaskDelete 后，暴露 pthread_cancel 缺失。这说明演示通过不能证明全部 OSAL API 可用。

遇到这种问题，应决定是否补齐目标能力或明确限制接口，不能只写一个空成功返回来掩盖生命周期语义。

编译器、SDK 与链接脚本要配套

输入 负责什么 典型问题
交叉工具链 ARM 指令、ABI 与辅助函数 混用主机对象、浮点 ABI 不一致
SDK 头与库 目标配置和实际可用实现 有声明无符号，旧头遮盖新头
链接脚本 入口、段和内存布局 加载地址或入口不匹配
构建与安装目录 保留一组一致的目标产物 主机/ARM、标准/EDS 混用

历史构建使用 Cortex-A9、ARM 指令集、soft-float 和 freestanding 等选项，这些选择与当时 SDK 配套。-T 的脚本控制 ELF 入口；-u app_main 用于要求解析应用符号，并不会把 ENTRY(boot) 改为应用函数。

以上是诊断命令示意，文件名按实际产物替换；交叉目标通常使用匹配的工具前缀。进一步看 map 文件，确认符号来自哪个归档成员。

验证结论留在实际执行的范围内

历史标准示例在 Linux 和 QEMU 完成了双订阅者、NOOP/HK。没有由此验证所有 OSAL 接口、完整服务、真机或长期竞争。后续增加能力时，先补一个能强制链接并运行该路径的小程序，再接回业务系统；这样 SDK、链接和运行问题会更容易定位。
